# 1. Phase Overview

The platform can now:

* Authenticate users
* Upload documents
* Build the knowledge base
* Answer enterprise questions

However, every authenticated user still has access to every document.

In a real enterprise, this is unacceptable.

Different departments contain confidential information that must only be accessible to authorized users.

Examples include:

* Employee salaries
* Financial statements
* Security incident reports
* Legal contracts
* Executive strategy documents

This phase introduces the Authorization Layer of the Enterprise Knowledge Assistant.

The system will determine not only **who the user is**, but **what they are allowed to access**.

---

# 2. Business Objective

Every answer generated by the AI must respect company permissions.

The AI should never retrieve information that the user is not authorized to access.

For example:

Employee

↓

"Show me next quarter's financial forecast."

↓

Finance document retrieved?

❌ No

↓

Access denied.

Likewise:

HR

↓

"What is the maternity leave policy?"

↓

HR document retrieved

↓

✅ Allowed

Authorization must occur before retrieval and answer generation.

---

# 3. Why This Phase Exists

Authentication identifies users.

Authorization determines what those users are permitted to do.

Without RBAC:

* Finance reports become public.
* HR records become visible.
* Confidential policies leak.
* Audit compliance fails.
* Organizations cannot trust the platform.

Authorization is therefore a core enterprise requirement.

---

# 4. Phase Goals

By the end of this phase the platform should support:

* Role-based permissions
* Protected document access
* Route-level authorization
* Document-level authorization
* Department-level authorization
* Access denial responses
* Permission middleware
* Permission validation before retrieval

---

# 5. Business Requirements

The platform shall:

* Restrict access based on user role.
* Restrict access based on document ownership.
* Restrict retrieval before the RAG engine executes.
* Prevent unauthorized citations.
* Prevent unauthorized embeddings from being searched.
* Log access denial events.
* Support future fine-grained permissions.

---

# 6. Non-Functional Requirements

Security

Authorization decisions must always occur on the server.

The frontend must never determine permissions.

Performance

Permission validation should add minimal overhead.

Maintainability

Authorization logic should remain independent of:

* FastAPI routes
* RAG engine
* Database models

Scalability

Future support should include:

* Department permissions
* Team permissions
* Document ACLs
* Custom permission policies
* Attribute-Based Access Control (ABAC)

# 12. Engineering Decision Log

## Decision 1

Authorize before retrieval.

Reason

Unauthorized documents should never participate in semantic search.

Benefits

* Better security
* Better performance
* Cleaner citations

---

## Decision 2

Keep authorization separate from authentication.

Reason

Authentication answers:

Who are you?

Authorization answers:

What may you access?

Keeping them separate improves maintainability.

---

## Decision 3

Implement server-side authorization only.

Reason

Frontend checks can be bypassed.

Benefits

* Enterprise-grade security
* Zero trust architecture

---

## Decision 4

Document-level authorization.

Reason

Departments often share repositories.

Not every HR document is public to all HR staff.

The architecture should support document-level permissions from the beginning.

---

## Decision 5

Future-proof for ABAC.

Although the MVP uses RBAC,

the architecture should allow migration to:

* Attribute-Based Access Control
* Policy engines
* Dynamic permissions

without major redesign.
